Designing privacy boundaries for a live translator

From building NavTranslate, a live speech and text translator built with Next.js and PostgreSQL

A translator handles data people naturally assume is private: microphone input, typed messages and a searchable record of past conversations. The interesting engineering problem was therefore not just how to translate text, but where that text is allowed to travel, when it is stored and who can retrieve it later.

Start by drawing the data boundaries

NavTranslate has four distinct trust zones. Keeping them explicit makes each privacy decision testable instead of leaving it as a vague promise in the interface.

The Web Speech API turns speech into text in the browser. Browser implementations may still use a cloud recognition service, so the interface should never claim that audio is guaranteed to stay on-device. Once a final transcript exists, the app sends text—not a recording—through its own server route for translation.

Guest mode should be genuinely temporary

Requiring an account before someone can test a translator adds friction and encourages unnecessary data collection. Guests can therefore use every core translation feature, but their recent items live in sessionStorage. They are scoped to the current tab and disappear with the browser session.

That choice also simplifies the server contract: an unauthenticated request can translate, but it cannot create a database record. Logging in changes the storage capability, not the quality of the translation.

Privacy is a backend rule, not a label. The server independently checks the signed session and the account's save-history setting before writing. A modified client cannot turn a guest request into stored account history.

Every history query carries ownership

Authenticated history introduces a classic multi-tenant failure mode: looking up a conversation by its ID alone. An unpredictable ID is not authorization. Reads and deletes must include the session's user ID in the database predicate.

const conversation = await prisma.conversation.findFirst({
  where: { id: conversationId, userId: session.userId }
});

The same rule applies to search, delete-one and delete-all operations. The route obtains identity from a signed, HTTP-only cookie, never from a user ID supplied by the browser. Passwords are hashed with bcrypt, while the cookie is SameSite=Lax and marked secure in production.

Keep providers behind one narrow route

The default provider, MyMemory, accepts relatively small UTF-8 requests. NavTranslate splits longer input on character boundaries while measuring encoded bytes, translates each chunk and reassembles the response. This avoids cutting through a multi-byte character—especially important for Mandarin, Japanese and Korean.

Both the free provider and the optional OpenAI path sit behind /api/translate. Zod enforces the language pair, mode and 4,000-character limit; an IP-based limiter contains abuse; timeouts prevent stalled upstream calls; and logs record the error type without copying the user's text.

For an LLM provider, the instruction also says to treat submitted text as content rather than commands. Translation input is untrusted input, even when it looks like a prompt.

The honest limits matter

This architecture reduces exposure, but it does not make translation confidential by magic. The chosen speech engine and translation provider remain data processors. An in-memory rate limiter only protects one application instance, and account recovery, CSRF hardening and encrypted history would be required before treating the app as a mature public service.

Those limitations are documented because a security boundary is useful only when users and future maintainers know exactly where it ends. The full implementation is in the NavTranslate repository.
